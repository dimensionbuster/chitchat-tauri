# 네트워크 계층 검토와 재설계

기존 Electron 앱(`chitchat-web`)의 네트워크 코드를 검토하고, Tauri 이전과 함께 다시 설계한 내용과 시험 결과를 정리한다.

## 1. 기존 코드에서 확인한 문제

| 영역 | 문제 | 영향 |
|---|---|---|
| 구조 | 직접 만든 WebRTC 스택이 **세 벌** (채팅 초기 동기화 v3 1,370줄, 와치파티 초기 동기화 1,293줄(사실상 복붙), 직접 파일 전송 1,103줄). 각각 offer/answer/ICE/청크/ACK/재개를 따로 구현 | 같은 버그가 세 곳에 존재, 수정 시 불일치 |
| 시그널링 | 모든 제어 메시지를 Yjs awareness 키로 전달(`fileTransferOffer-*`, `profileTransfer-*` 등), 변경 이벤트를 폴링하듯 처리 | 상태가 모든 피어에 복제되고 정리 타이밍 버그 |
| 흐름 제어 | 신뢰성 채널(DataChannel) 위에 **자체 ACK/재전송**. ACK 창 10청크×32KB 고정 | RTT 100ms에서 이론상 최대 약 3MB/s. 버퍼는 `sleep(20~100ms)` 폴링 |
| 완료 처리 | 최대 재시도 후 "강제 완료" 경로 | 데이터가 빠졌는데 성공으로 처리될 수 있음 |
| 메모리 | 수신 청크를 `Map`에 모았다가 한 번에 병합 → Blob | 큰 파일은 수신 중 메모리 2배 이상 |
| 문서 비대화 | 256KB 이하 파일을 base64로 **Yjs 문서 메타에 직접 포함** | 모든 피어에 영구 복제, 새 접속자 동기화마다 전송 |
| 프로필 사진 | awareness 키에 base64 이미지를 실어 전송 | 접속자 수만큼 반복 전송 |
| 리스너 | 연결 복구마다 `awareness.on('change')` 등록 | 중복 처리, 누수 |
| 초기 동기화 | 접속 때마다 최대 약 8초 블로킹(오버레이) | 로컬 기록이 있어도 네트워크가 느리면 입장이 느림 |

## 2. 새 구조

```
UI (Vue)  ──  composables/ (얇은 바인딩)
                │
core/ (프레임워크 독립 TS)
  mesh.ts        Trystero 룸 1개 = 피어 연결 1세트. 채널(Yjs, 파일 제어, 파일 데이터)이 연결을 공유
  provider.ts    Yjs 문서/awareness 동기화 (sync step 1/2 — state vector 교환)
  room.ts        문서 + IndexedDB + 메시 + 전송 서비스 조립
  net/transfer.ts  파일 전송 서비스(스웜 다운로드 + 서빙)
  net/protocol.ts  제어 메시지/메타 검증
  net/blobs.ts     디스크 블롭 저장소 클라이언트
Rust (src-tauri)
  blobs.rs       해시 id 블롭, 위치 쓰기, 스트리밍 해시, 이어받기용 flush
```

- 파일 id = 내용의 SHA-256. 출처를 신뢰할 필요가 없고(완료 후 검증), 중복 제거가 자동이다.
- 파일은 1MiB 구간으로 나눠 **보유한 모든 피어에게 병렬 요청**한다. 구간은 도착 즉시 디스크에 쓴다.
- 구간마다 SHA-256 앞 16바이트를 함께 보내 **구간 단위로 손상을 잡는다**. 파일 전체는 마지막에 SHA-256으로 확정하며, 불일치하면 처음부터 다시 받는다(최대 2회).
- 피어별 윈도우는 처리량(EWMA)×4초로 정한다. 정체 판정은 "구간 완료"가 아니라 **수신 진행 이벤트**(바이트가 도착 중인지) 기준이다.
- 이어받기: 구간 비트맵을 디스크 flush 이후에 저장한다(비트맵이 디스크보다 앞서지 않도록).
- 그 룸의 파일 목록에 있는 id만 알리고 제공한다(다른 룸의 보유 파일 노출 방지).
- 제어 메시지는 전부 스키마 검증 후 처리한다. 길이/범위가 규격을 벗어나면 버린다.
- 네트워크를 기다리지 않는다: 로컬 기록은 즉시 표시하고 오프라인에서도 글을 쓸 수 있다(Yjs가 나중에 병합).

삭제된 코드: `useInitialSync.v3`, `useWatchPartyInitialSync`, `useDirectFileTransfer`, `useFileTransfer`, `useWebrtcConnection`, `useGlobalDataChannelQueue`, `useFileTransferState`, 시그널링 서버 클라이언트, Firebase 푸시, IndexedDB 파일 캐시 (총 약 7,000줄).

## 3. 시험 환경

Windows의 실제 Tauri 앱(WebView2) ↔ **WSL2의 Chromium**(별도 NAT 네트워크, 다른 네트워크 스택). `tools/netlab/` 참고.
같은 PC 안 두 창 테스트와 달리 실제 NAT 통과, 지연/손실/대역폭 제한(`tc netem`)을 적용할 수 있다.

## 4. 결과

| 시험 | 결과 |
|---|---|
| 다른 네트워크 스택 피어 연결 | 9초 (공용 Nostr 릴레이 경유), UDP |
| 100MB 양방향 | 통과, SHA-256 검증 |
| **2GB 수신** | 통과, 331초, 평균 6.2MB/s, **수신 중 메모리 증가 없음**(약 520MB 평탄) |
| 송신 피어가 전송 중 이탈 → 복귀 | 통과. 오류 없이 대기 후 자동 재개 |
| 수신 앱 전송 중 재시작 | 통과. 49MB 중 48MB 지점에서 재개 |
| 송신 측 손상 데이터 | 통과. 최종 해시 검증이 감지하고 재시도로 복구 |
| 보유 피어 2명에서 동시 수신 | 통과. 두 소스 모두 사용 |

### 처리량의 한계 (이 시험 환경 기준)

- 랩의 원시 UDP는 260MB/s로 보내도 약 16MB/s만 수신된다(WSL2 가상 스위치). WebRTC 전용 채널 상한이 약 7.4MB/s이고 앱은 그 약 95%(6.8~7.0MB/s)를 낸다. **7MB/s는 앱이 아니라 시험 환경의 한계**다.
- 고지연/손실에서는 단일 SCTP 연결이 느리다: RTT 100ms 약 0.7MB/s, RTT 100ms+손실 1% 약 0.06MB/s. 전용 DataChannel로 우회해도 개선 폭은 제한적이다(약 1MB/s). 연결을 여러 개로 나누는 방식(아래)이 효과적일 것으로 보인다.
- 이런 조건에서도 전송은 **느리지만 끊기거나 깨지지 않고** 진행률이 부드럽게 갱신된다.

## 5. 알려진 한계와 다음 작업

- 고지연 링크 처리량: 룸을 추가로 열어 파일 전송 전용 RTCPeerConnection을 여러 개 쓰는 방안(레인). 아직 구현하지 않았다.
- NAT 통과 실패(대칭 NAT)는 TURN 없이는 불가. 연결 실패를 UI에 명확히 표시하는 작업이 남았다. 구조상 `turnConfig`를 붙일 자리는 열려 있다.
- 시험은 한 PC의 WSL2와 한 쌍의 NAT였다. 실제 서로 다른 가정/모바일 회선에서의 확인은 별도로 필요하다.
- 시험하지 못한 것: 디스크 가득 참(구현은 `no-space`로 처리), 3명 이상의 동시 업로드, 매우 오랜 시간(수 시간) 전송.
